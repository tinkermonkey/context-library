## The core chain: `adapters → sources → source_versions → chunks → entity_links`

This is the path a single piece of content takes through the schema, and it's the non-obvious part of the design (chunks don't point directly at their source; they point at a specific *version* of their source):

1. **`adapters`** — one row per configured adapter instance (`adapter_id` is the adapter's stable identity, e.g. `"apple-imessage"`). Declares which of the 8 domains it feeds and which `normalizer_version` it's currently running.
2. **`sources`** — one row per distinct origin the adapter fetches from (a single email thread, a single calendar, a single contact list). `current_version` is a denormalized pointer to the latest row in `source_versions` for this source — it's what lets `chunks` filter to "only the chunks belonging to the current version" without a subquery (see `query_chunks_by_identifiers()` in `document_store.py`, which joins on `c.source_version = s.current_version`).
3. **`source_versions`** — one row per `(source_id, version)`, holding the full normalized markdown for that version and the complete set of `chunk_hashes` produced from it (as a JSON array). This is what makes diffing a set operation: comparing `chunk_hashes` between two versions of the same source tells you exactly which chunks were added/removed, no positional alignment needed.
4. **`chunks`** — one row per `(chunk_hash, source_id, source_version)`. The **compound primary key is deliberate**: the same `chunk_hash` can legitimately recur across different `source_id`/`source_version` combinations (identical content re-appearing, or persisting unchanged across a version bump — `chunks.chunk_hash` is a content hash, not a row identity). `retired_at IS NULL` is what "active" means; a chunk is never deleted, only retired, when its source is re-ingested and that chunk's hash no longer appears in the new content.
5. **`entity_links`** — the one table that references `chunks.chunk_hash` **without carrying `source_id`/`source_version`**, and without an FK constraint at all (see the comment directly above the table in `schema.sql`). This is intentional, not an oversight: because the same `chunk_hash` can exist under multiple `(source_id, source_version)` rows, a strict FK to the compound `chunks` primary key isn't expressible for a bare hash reference. The tradeoff is that `entity_links` rows are cleaned up procedurally (`EntityLinker._cleanup_retired_chunks_links()`, via `DELETE ... WHERE NOT EXISTS`) rather than via `ON DELETE CASCADE`.

## Supporting tables (soft references, no FK)

- **`lancedb_sync_log`** — an append-only queue of `(chunk_hash, operation)` pairs recording pending vector-store operations, read by whatever process reconciles ChromaDB/LanceDB against SQLite. Like `entity_links`, it references `chunk_hash` without an FK, for the same reason (a bare hash doesn't identify one `chunks` row).
- **`dead_letters`** — per-`(adapter_id, source_id, error_type)` upserted failure records for items that were skipped mid-ingestion so the rest of a page could commit. No FK to `adapters`/`sources` because a dead letter needs to survive even if the source row itself was never successfully created (the whole point is to record failures that happened *before* a clean row could be written).

## Indexes

Every foreign-key-shaped column has a supporting index (`idx_sources_adapter`, `idx_source_versions_adapter_id`, `idx_chunks_source`, `idx_chunks_adapter`, `idx_entity_links_source`, `idx_entity_links_target`, `idx_dead_letters_adapter`, etc.) — see `schema.sql` for the full list. `idx_chunks_retired` and `idx_chunks_domain` back the two filters (`retired_at IS NULL`, `domain = ...`) that appear in nearly every read query in `document_store.py`.

## Regenerating this diagram

There's no automated ERD generation in this repo (no dbdocs/SchemaCrawler wiring). If the schema drifts from this file, the fastest way to regenerate the Mermaid block is to point `schema.sql` at any Mermaid-aware SQLite introspection tool (e.g. `mermerd`, or SchemaCrawler's Mermaid renderer) against a freshly-migrated `documents.db`, then fold in the "unenforced reference" annotations above by hand — those relationships exist by convention in application code (`entity_linker.py`, `document_store.py`), not as schema constraints, so no generator will infer them automatically.
